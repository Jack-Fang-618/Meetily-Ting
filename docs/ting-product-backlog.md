# Ting 产品讨论与待改清单

更新日期：2026-10-22（香港时间）

本文持续记录试用 Meetily 开发版时发现的产品调整事项。用于后续集中讨论和实施，不代表所列能力已经实现，也不授权现在展开全部改动。开发环境记录见 [ting-dev-setup.md](ting-dev-setup.md)。

## 已确认的产品方向

- 最终产品是 Ting：围绕音频转录、上下文辅助核验、人工确认，再按需总结。
- 学习旧 Ting 背后的目标和抽象，结合 Meetily 的实际架构设计；不预设复用旧 Ting 代码、页面或数据结构。
- 保留全本地运行能力，同时支持用户主动选择云端 STT 或 LLM。
- 保留原始音频与原始 ASR，区分 AI 建议和人工确认。上下文合理性不能代替音频证据。
- 当前先跑通开发版基本流程；以下产品改动暂缓，之后一起审议、实施。

## 待改事项

### 01 — 欢迎页与隐私文案

状态：已记录，待设计和实施。

当前欢迎页包含：

- `Welcome to Meetily`
- `Record. Transcribe. Summarize. All on your device.`
- `Your data never leaves your device`
- `Intelligent summaries & insights`
- `Works offline, no cloud required`
- `Takes less than 3 minutes`

用户指出：加入云端转录或总结后，不能继续无条件声称所有处理均在设备上、数据永不离开设备。

拟调整方向：

- 欢迎页逐步使用 Ting 产品名称，保留适当的 Meetily 开源归属及许可说明。
- 表达“支持全本地；云服务由用户选择”，避免绝对的数据不外传承诺。
- 在产品主线中体现转录、核验和人工确认；总结为可选后续步骤。
- 将“可离线工作”限定为已具备所需本地模型、组件的使用方式。
- 设置耗时受模型下载、网络与权限配置影响，重新评估“三分钟以内”的承诺。
- 最终文案、语言和布局尚未确定，不在云功能未实现时宣称已经支持。

验收要点：欢迎页、设置、关于页等相关位置的表述与实际行为一致。

源码线索：`frontend/src/components/onboarding/steps/WelcomeStep.tsx`、`frontend/src/components/About.tsx`。

### 02 — 首次设置按处理环节分别选择

状态：讨论方案，待确认交互和实现。

| 环节 | 拟提供选择 | 云端处理涉及的数据 |
| --- | --- | --- |
| STT 语音转录 | 本地 / 云端 | 音频及适配器实际需要的参数、上下文 |
| AI 核验 | 本地 / 云端 / 暂不启用 | 转录文本与用户选定的上下文；若涉及音频复核，须另外明确 |
| 总结 | 本地 / 云端 / 暂不启用 | 选定版本的转录文本及总结所需上下文 |

- 各环节独立配置，支持本地转录加云端总结等混合方式。
- 选择云端的用户，不应被强制要求下载不使用的本地模型。
- 用户应能暂缓配置可选环节，之后在设置中补充或更改。
- 具体供应商、模型、默认值与 API Key 管理方式，待架构审查后决定。

验收要点：纯本地、混合与云端路径均有清楚的设置过程；不把下载某个固定模型作为所有用户的必经步骤。

源码线索：`frontend/src/components/onboarding/steps/SetupOverviewStep.tsx`、`frontend/src/components/onboarding/steps/DownloadProgressStep.tsx`、`frontend/src/contexts/OnboardingContext.tsx`。

### 03 — 云端选择与数据流向说明

状态：原则已记录，具体交互待设计。

- 默认保留本地路径；云端处理必须由用户明确选择。
- 在选择云服务时说明服务商、发送的数据类型，以及该设置作用于哪些任务。
- 本地模型失败时，不得静默切换云服务。
- 不把云端模型输出自动视为经过人工确认的记录。
- 保留全本地模式，实际核查网络行为后再确定对外隐私承诺的范围。

验收要点：用户能够判断一次操作会不会发送音频、转录文本或上下文，以及发送给谁。

### 04 — Setup Overview 的快速开始路径

状态：用户确认方向，待设计和实施。

当前页面声称必须下载转录和总结模型，并把两个下载步骤作为开始使用的前提。未来应让用户选择下载本地模型或配置 API；总结可暂不启用。仅下载当前所选路径需要的模型。

配置 API 的具体字段、服务商兼容性校验、连接测试及密钥保存方式另行设计；不能假设支持聊天接口的服务也支持音频转录接口。尚未接入云 STT 前，不提前展示可用承诺。

验收要点：已配置可用云 STT 的用户，无需下载本地转录或总结模型即可开始转录；纯本地路径仍完整可用。

### 05 — 项目入口与问题反馈链接

状态：用户提出调整，待实施。

- Ting 的项目主页入口指向 `https://github.com/Jack-Fang-618/Meetily-Ting`。
- `Report issues on GitHub` 应指向本项目的 Issues 页面，实施时确认 fork 已开启 Issues。
- 上游来源、许可证、作者归属和依赖来源链接保留各自真实目标，不进行全局替换。
- 发布、下载和更新入口需单独配置，不能仅替换 GitHub 仓库名称就视为可用。

验收要点：用户能把 Ting 问题提交到我们的项目，同时仍能找到 Meetily 上游及其许可信息。

### 06 — 上下文输入与可复用的项目背景包

状态：用户确认希望做，暂不实施；命名及交互待设计。

当前观察：截图中的输入框标明供 AI summary 使用，示例为参会者、会议背景与目标。用户希望将其扩展为核验转录也可使用的上下文入口，减少每次重复打字。

目标：

- 保留文字输入，增加语音补充背景的入口。语音转成可编辑草稿，由用户检查后再作为上下文使用，避免口述识别错误成为事实。
- 可选择以前使用过的项目背景包（暂称 Context Pack）：项目背景、人员与机构名称、术语、缩写、语言习惯及已确认的相关信息。
- 同一项目的多次会议复用背景包，同时允许添加仅属于本次会议的补充说明。
- 背景包回答“这是什么项目、有哪些背景”；输出模板规定“结果如何组织”。两者是不同概念，不混成一个 Template 菜单。
- 用户能知道本次任务选中了哪些包，以及它们用于转录提示、AI 核验还是总结。是否给 STT 使用、如何适配需另行设计。

设计约束与建议：记录包的来源、版本、作用范围及每次处理实际使用的快照；AI 猜测不自动沉淀为背景事实，人工修改是否收录应由用户确认。背景只辅助判断，不能替代音频证据。

待定：包的创建与编辑入口、多个包冲突处理、项目归属方式、语音输入使用哪个 STT，以及包更新是否触发历史录音重处理。

验收要点：两次会议能复用同一背景包并保留各自补充内容；口述内容可检查修改；历史结果能追溯当时采用的上下文。

### 07 — 从总结面板扩展为转录核验工作台

状态：用户确认产品方向，布局和技术方案未定，暂不实施。

用户希望利用现有转录区和右侧总结区，形成一个能完成校验、回听、人工修改、再次交给 AI 处理的综合工作台。现有布局是候选承载位置，不代表已经决定把全部功能塞进一个面板。

目标流程：原始 ASR → AI 初审／整理稿 → 可追溯的自动修订与待核实项 → 用户回听、修改和反馈 → 按需重新核验 → 可选总结。

- 用户希望依据充分的高置信错误先由 AI 修正，低置信和存在歧义的内容反馈给用户处理。
- “高置信”的判定与自动应用策略仍需设计；LLM 自报置信度不能视为声学证据。所有自动修改必须保留原文、差异和来源，可回退；证据不足则标记，不猜写。
- 待核实项关联对应音频位置，支持反复回听；时间定位为估算时要明确说明。
- 用户可接受建议、手动改写、保留原文、暂缓处理，并补充说明或背景，让 AI 再处理指定问题或相关片段。
- 再处理不得静默覆盖人工确认内容，保留版本及本次反馈。具体锁定／冲突机制待设计。
- 区分原始转录、AI 修订、人工确认状态，以及可读性整理、总结等派生结果；不能把生成了新稿等同于全文已确认。
- 模型、语言和输出模板仍可配置，但核验规则与总结模板需分别表达。

界面澄清：截图中的 Auto 与总结语言选择有关；源码 `frontend/src/components/SummaryLanguageSettings.tsx` 明确 Auto 使用转录文本的主要语言。不能据此认定当前已有全文自动翻译功能。

验收要点：一个不确定片段可以完成“定位回听 → 用户修订／补充背景 → 再次核验”，全程可比较原文与修改，也能区分尚未确认的内容。

### 08 — 围绕总结对话，并可选联网搜索

状态：用户特别希望做，后续规划项，暂不实施。

目标：总结生成后仍可继续提问和讨论；除基于会议材料的讨论外，可按用户选择使用具有外部搜索能力的 AI，引入外部资料。

- 区分“只用会议材料回答”和“联网查资料”；云端 LLM 调用不自动代表启用网络搜索，两项能力分别配置和说明。
- 明确对话读取的是总结、选定转录版本、用户选择的片段，还是项目背景包，避免默认发送所有材料。
- 联网答案应区分会议中说过的内容、外部来源与模型推断，并提供可检查的来源；外部资料不自动写回转录或变成项目背景事实。
- 对话与总结关联使用的材料版本；核验结果更新后，如何刷新总结和对话上下文需另行设计。

待定：供应商与搜索工具、对话存储、上下文长度、版本更新方式、是否允许用户选择脱敏或摘录后发送。当前不承诺特定供应商具备联网能力。

验收要点：用户能仅基于本地材料对话，也能明确选择联网扩展；回答中的外部信息与原会议内容可区分。

### 09 — 外部处理告知与录音提醒

状态：用户明确重视，保留并扩展这一设计方向。

用户反馈：录音时出现“是否已经通知所有参会者正在录音”的提醒，这个功能很好，应保留。此为用户观察，尚未审查其全部触发条件。

- 开始录音时保留参与者告知提醒。提醒本身不等于已经获得所有人的同意。
- 使用外部 API 前，应清楚告知即将发送什么、发送给哪个服务、用于什么功能，并给出继续或取消的选择。
- 录音告知、云端处理选择、联网搜索选择分别处理，不能以同意录音代替同意向外部发送会议材料。
- 搜索查询本身也可能暴露项目名称、人物或敏感问题；外部 LLM 和搜索服务可能是不同接收方，要分别说明。
- 语音补充背景若走云端，同样需要清晰说明音频去向。
- 告知应发生在传输前，而不是发出后才弹通知。如何保存选择、何时再次提示，待交互设计，避免机械重复打扰。
- 不对第三方的数据留存或训练用途作未经核实的承诺。

验收要点：用户可以在传输前了解并取消外部处理；纯本地模式不因对话或失败重试而静默联网；录音提醒得到保留。

### 10 — 转录稿与总结的便捷整理、复制和导出

状态：用户确认希望支持，具体格式、交互与实施顺序待规划；暂不实施。

用户目标：方便把 transcript 和 summary 输出为可复用、可分享的文档，支持 Markdown，以及 Word、PDF 等常见格式。

拟设计能力：

- 转录稿、总结可分别导出，也可选择合并为一份文档。
- 支持 Markdown（.md）、Word（.docx）、PDF（.pdf）；便捷复制 Markdown 作为候选快捷操作。
- Markdown 保留标题、段落、列表等结构；Word 便于继续编辑；PDF 用于固定版式的阅读和分享。
- 区分导出时的排版整理与内容改写。普通导出不静默润色、修正或总结原文。

待确认的导出选项与约束：

- 明确导出原始 ASR、AI 修订稿还是人工审核后的版本；有待核实内容时，不将其标成全文已确认。
- 时间戳、说话人、待核实标记、修改记录是否包含，提供适当选项；正文与审核附录的具体组织待设计。
- 合并导出时标明总结所依据的转录版本，避免把旧总结与新修订稿误呈现为一致结果。
- 项目背景包、私有备注和对话记录不默认随转录稿一起导出；需明确选择范围。
- 优先在本地生成文档，不应为导出格式而要求用户把会议内容上传第三方。
- 若以后支持导出联网讨论，保留必要的来源引用，区分外部资料与会议记录。

验收要点：能便捷获得可编辑的 Markdown 和 Word，以及正常排版的 PDF；中英文混排、长段落、列表和分页可读；所选版本、导出范围与生成文件一致。

尚未调查现有 Meetily 的完整导出能力，实施前先核查已有功能，再确定扩展范围；本条不预设必须重写导出模块。

### 11 — 播放器、逐字稿与待核实问题联动

状态：用户提出明确的目标交互，暂不实施；具体布局与参数待设计。

用户观察：当前左侧主要是转录文字，缺少其期望的直观播放器体验。此为用户对当前页面的反馈，不据此认定整个 Meetily 没有回放功能。

目标布局与操作：

- 左侧结合音频播放器与逐字稿，提供播放、暂停、进度定位等基础操作。
- 右侧呈现 AI 标记的不确定片段、候选修正及核验信息。
- 点击右侧某个问题，左侧自动滚动到对应原始转录位置并高亮，播放器定位到相关音频。
- 回听包含问题前后各几秒的上下文，而不是只播放一个孤立词；前后时长是否可调、默认值待设计。
- 用户可重复播放该片段，听更长的上下文，暂停后纠正文本或处理建议；处理后更新问题状态，仍可回溯原文与音频。

待设计细节与约束：

- 点击问题后自动播放，还是定位后由用户点播放，待确认；不把自动播放当作已定行为。
- 片段播放是否在结束点自动停止、是否循环、是否提供速度调节，待确认。
- 区分播放位置、当前选中问题和编辑位置，避免播放器更新导致用户编辑时视图不断跳动。
- 修订后的文字仍应关联原始音频时间和原始文本锚点；文字长度变化不能让回听位置失准。
- 优先使用真实词级／片段时间；只有估算定位时明确显示，不伪装成精确定位。
- 前后扩展范围需裁剪到音频起止边界；音频缺失或不可用时明确提示。
- 不确定项的建议、原始 ASR、人工处理结果保持可比较，修改不能覆盖原始证据。

验收要点：点击任一待核实项，可以定位原文、播放包含上下文的相关音频，并完成修订；编辑后再次点击仍定位正确。播放器与问题联动应作为核验工作台的核心能力，而非仅增加一个独立播放按钮。

与第 07 项共同规划；实施前核查现有音频保存、回放组件与时间戳数据是否足以支撑，不预设重做整套播放器。

### 12 — 官网下载与非技术用户的完整交付体验

状态：用户明确要求纳入开发规划，暂不建设或发布；收费与商业模式另议。

目标用户不需要懂代码，也不需要安装 Codex、Git、Node、Rust、Xcode 或其他开发工具。正常路径应为：进入官网 → 下载适合电脑的安装包 → 安装打开 → 完成简明设置 → 开始录音或导入文件。

规划范围：

- 官网作为产品介绍、下载、使用帮助和问题反馈入口；明确区分官方网站与桌面应用内界面，不因“官网／前端”措辞而默认改做浏览器应用。
- 提供可直接运行的桌面安装包；按平台与芯片架构提供清楚的下载选项，避免让用户 fork、clone 或自行编译。
- 必要运行组件随安装包提供，或由应用可靠地管理安装。模型体积较大时可首次按需下载，但需解释用途、大小、进度和失败后的处理方式。
- 首次设置提供本地模型与云端 API 的适用路径；云端路径如需用户自己的 API Key，要有易懂引导，不能把“无需编程”误写成“任何配置都不需要”。
- 录音权限按功能请求；只导入文件的用户不应被录音权限阻挡。
- 下载、安装、首次启动、权限、模型准备、首次成功任务是一条完整的验收路径，不只验证开发模式能运行。
- 更新和卸载体验纳入规划，升级需保留用户数据；应用更新通道应属于 Ting，目前关闭的上游更新通道不能直接重新启用。

发布前需评估并完成的工作：

- macOS 应用打包、签名、公证及所需发布凭据；Windows 安装包、签名与安装体验；其他平台的交付顺序待定。不能要求普通用户关闭系统安全保护来安装。
- 干净环境验证：没有开发工具的电脑能安装、启动并完成第一次任务；检查运行依赖、模型下载失败、升级后的数据兼容性。
- 官网说明、版本号、发布说明、下载文件与应用内版本一致；发布产物可验证来源。
- 保留上游许可和归属说明；明确隐私与本地／云端的数据流向。

推进建议（尚未确定排期）：当前继续核心架构调查；首个可用功能稳定后建立 macOS 可分发测试包；在对外试用前完成最小官网、下载和帮助入口，并验证非技术用户上手。平台顺序、域名、托管、签名账号和发布方式另行确认，不在本条中授权购买或公开发布。

### 13 — 可选的新手学习支线与灵活的数据处理路径

状态：用户明确希望纳入规划，暂不实施；教育内容、路径名称与交互待设计。

目标：首次引导让不熟悉技术的用户理解选择，但学习内容不能成为必须完成的教程。熟悉的用户可以直接配置；需要帮助的人可以进入支线，阅读后回到原步骤，保留已有选择。

可选学习内容：

- 用普通语言解释 API：应用通过接口把选定内容交给另一项服务处理，再接收结果；云端 API Key 的用途及可能产生的服务商费用。
- 解释本地与云端处理位置、联网需求、硬件与模型下载要求，以及不同方案对速度、质量和隐私的影响。
- 不把“云端必然更好”或“本地必然效果差”作为固定结论；实际效果取决于模型、语言、任务和硬件。
- 解释云端可能接收到的音频、逐字稿、摘要、背景包或查询；服务商的保存、日志、训练用途和删除政策须按具体服务核实，不能统一承诺“不保存”。
- 学习支线可跳过，但不能以跳过教程代替实际外发前的数据流向告知与明确选择（见第 09 项）。

用户最新确认：面向用户的选择收敛为以下三条路线，替代此前零散列出的混合路径；不提供任意组合流程作为默认新手界面。

| 路线 | 目标流程 | 适用场景与边界 |
| --- | --- | --- |
| 全本地 | 本地转录 → 本地核验／整理（如启用） → 本地总结（如启用） | 对隐私敏感的会议；处理内容不外发 |
| 全云端 | 云端转录 → 云端核验／整理（如启用） → 云端总结（如启用） | 用户判断内容适合外发并明确选择；音频和后续文本可能发送给所选服务商 |
| 本地去敏后云端总结 | 本地转录 → 本地去敏 → 检查待发送版本 → 云端总结 | 原始敏感音频、逐字稿保留在本地，仅发送经过本地去敏且用户允许的版本 |

“全云端”指 AI 处理路线，不代表所有数据必须云端存储；存储策略另行设计。总结仍为可选步骤。

明确排除：不将“本地转录 → 云端去敏 → 云端总结”作为隐私保护路线。先上传原始敏感文本再去敏，已经发生了原文外发，不能达到本地去敏的目的。

选择依据：用户可以根据每次会议的性质选择路线，例如私密会议优先全本地，适合外发的日常讨论可选全云端。云端有机会使用更强或更新的模型，提高质量和处理效率，但不能承诺必然优于本地；具体仍取决于模型、语言、网络和任务。全本地减少向外部服务暴露会议内容，但不等于自动具备所有安全保障。

设计约束：

- 用户界面先提供三种容易理解的路线。第 02、03、04、12 项中的混合／API 设置方向按此收敛；内部模块保持解耦，不等于对用户暴露任意流程编排。
- 去敏模型／规则在本地运行。原始稿与去敏稿分开保留，不覆盖原始证据。
- 去敏可能遗漏；模型判断“没问题”不能作为自动外发的充分条件。提供可检查的发送版本和明确选择，确认粒度待设计。
- 去敏路径需检查实际请求包含的背景包、历史对话和元数据，不能在去敏正文之外又附带原始敏感材料。身份映射表如存在，留在本地。
- 去敏后的云端结果关联输入版本；不能把因去敏丢失的信息猜写回原会议记录。
- 核验模块在第三条路线的具体位置待设计；原始敏感音频／文本不得未经处理就外发核验。
- 以后若扩展联网对话，也必须遵守所选路线的外发边界，不能绕过去敏路径发送完整原稿。

验收要点：可跳过教育支线；能按会议选择三种路线；全本地不发送会议内容；全云端明确说明发送内容及接收方；去敏路径不在本地去敏前上传原始敏感材料，实际外发范围与用户检查的版本一致。

### 14 — 云端服务交付与成本模式（后期决策）

状态：用户要求纳入后期考量，尚未选型、定价或授权采购／上线；不阻塞当前架构调查。

未来给非技术用户交付云端功能，需要在以下方式之间选择，也可以分阶段提供：

- 用户自配 API（BYOK）：用户使用自己的供应商账号、密钥与额度；产品需提供易懂的配置说明。
- 产品托管云端服务：用户无需自行配置供应商 API，由 Ting 服务端管理供应商接入与用量。不能将开发者个人 API 密钥直接内置到分发的桌面安装包中。

待评估问题：

- 是否需要供应商的商业合同、企业方案、更高配额或并发限制，以及商用／转售条件；不同供应商要求需届时核实，不预设必须申请某种统一的“商业 API”。
- 托管方案的服务端认证、密钥管理、用量计量、预算与限额、滥用防护、故障处理和隐私责任。
- 若由产品承担模型成本，如何持续覆盖成本：订阅、按量额度、订阅含额度与超额计费等均为候选，未决定收费。
- 每种成本模式如何向用户解释音频转录、文本处理与不同模型的用量，如何处理失败、重试和额度不足。
- 先 BYOK 交付还是直接提供托管服务，待核心体验验证后决定。

边界：采用云端不自动意味着必须立刻建立完整商业收费体系；BYOK 与托管有不同的技术、成本和运营责任。当前只记录决策问题，不建设支付、计费或服务端商业基础设施。
